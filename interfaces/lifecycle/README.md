# Lifecycle Execution Adapter v1

This is a callable local reference implementation, not a GitHub or production-platform client. Default A remains the host Agent's method layer; optional B now includes the original security-record validator and the deterministic execution adapter in this directory. It uses the Python standard library and POSIX secure-file/locking capabilities, or the [limited native Windows backend](../../docs/windows-support.md); local merging also requires an existing Git that supports `merge-tree --write-tree`. There is no installer, network call, arbitrary shell configuration, automatic login, comment publication, or background task. The protocol follows the [core contract](../../skills/pre-pr-review/references/contract.md), [recheck/budget rules](../../skills/pre-pr-review/references/recheck.md), and each stage's design; it does not add another set of clearance statuses.

## Trust and Runtime Boundaries

- `--host-root` is a directory specified and protected by the user/host, containing policy.json, authority.json, state.json, and host verification records. `--policy-sha` must come from a trusted user/host channel, never from commands in the PR under review. The host protects directory contents/process permissions, PATH, HOME, and the actual Git executable. Git subprocesses retain HOME to support host wrappers, but global/system Git configuration and user attributes remain explicitly disabled, and injection variables such as GIT_DIR/GIT_CONFIG_COUNT are not inherited. Metadata in the managed bare repository must also be protected: CAS guarantees only a conditional update of the target ref, not protection against arbitrary concurrent changes to the Git directory layout. Hashes and JSON actor strings are neither authentication nor a sandbox.
- `--input-root` holds only untrusted tool results and raw evidence. ingest/observe/import-security read from it; init/adjudicate/advance/merge-prepare/delivery-plan read specified records from host-root. Tool imports contain no human approval fields and cannot write host authority. The host first filters data and secrets; instructions in logs are not executed.
- authority.json is a **host-side transcription** of decisions by authorized people: it recognizes only real people listed in policy, exact action/binding/policy matches, and unexpired, unrevoked records. An imported file cannot prove that a real person exists. A real-platform integration requires a trusted host to verify identity/qualification before recording the decision; an Agent must not self-sign. Append a later revoke with the same decision id; the latest record with that ID takes effect. The host must serialize authority updates; this implementation provides neither immediate remote revocation nor a cryptographic signing service.
- Session file locks coordinate only local processes that follow this interface; they cannot stop someone with file permissions from changing the ledger. The controlled directory must not be writable by the target project or parallel reviewers. Without this isolation, the program cannot serve as an enforced gate. The ledger has a 1 MiB limit and stops when it reaches that limit; deleting the ledger to reset usage is not allowed. Migration/archival must retain history and be handled explicitly by the host.
- Command exit 0 means only that a result was produced. Read recommendation/checks/reasons or the actual receipt; READY_FOR_NEXT never grants action authority. Errors exit 2 with UNKNOWN/HOLD; explicit budget errors produce REPLAN. An operational exception is not a product defect. The exact scopes of rounds, the operation ledger, and observations from the current invocation are described below; they do not claim to impose a hard budget on external models.

## Modules and Host Interfaces

| Module | Implemented responsibilities | Host requirements / capabilities still unavailable |
| --- | --- | --- |
| core.py / Session | Fixed policy, continuous ledger, bounded counters, time/identity, mapping of human decisions, atomic file replacement | Real authorization and policy trust, secret filtering, permission isolation, external-call accounting |
| review.py | Evidence and candidate imports, verification records, stable IDs/raw observations, duplicate links/disputes, version invalidation, four logical gates | Verification of original requirements/code semantics, actual CI retrieval and source authenticity; no automatic model or test-tool invocation |
| merge.py / LocalGit | prepare/preflight/execute/query; isolated bare-Git candidate, integration evidence, expected-old atomic ref update, actual-ref receipt | Supports only local SHA-1 bare repos with an explicit isolation marker and merge_commit; no arbitrary user repositories, remotes, squash/rebase, or queue providers |
| delivery.py / LocalSimulation | plan/read/apply/query, optional capabilities, bounded observation, idempotent requests and receipts; separate pause/off/rollback/forward-fix | Local simulated state only; no real deployment, propagation delay, metrics service, recovery, or proof of production health |
| host_delivery.py / host-injected object | Policy selection for deploy/rollback, exact intent, conditional pre-state, a single invocation, and receipt recovery | No built-in production connector; authentication, conditional updates, and durable idempotency must be supplied and accepted by the host |
| cli.py | Explicit command entry points for the capabilities above | Does not load arbitrary Python classes/plugins/commands selected by configuration |

Real connectors can implement the same responsibilities in a trusted host: retrieve identities/checks/human decisions read-only; fix the combination during prepare; verify valid evidence during preflight; execute with separate authorization and a reliable conditional update; query the actual result. A delivery provider's read/apply/query must return actual identity, idempotency correlation, and confirmed/failed/unknown results, respectively. Simply replacing function names does not establish atomicity/authority or production acceptance; the CLI currently selects only the two local backends. Report BLOCKED/UNKNOWN when a capability is missing; do not fall back to an ordinary merge or guess that it succeeded.

## Plan Integrity and Recovery Compatibility

Merge plans are checked during preflight, execution, and query against the complete canonical digest, policy-specified repository/target/method, source and combination identities, and actual Git commit/tree and ordered parents. New execution also recomputes the combination tree and rechecks current evidence and approval, using the same verified target for the expected-old update and result read. All-zero OIDs, ref names masquerading as commits, incorrect targets, and inconsistent objects are rejected before any write. Hashes check consistency; they cannot authenticate someone who can rewrite the trusted policy, approvals, and ledger together.

Merge receipts use `merge-receipt/v2`, binding operation, policy, repository, target_ref, base, and candidate. Query first verifies the plan/receipt association; a known failure cannot be attributed to a successful attempt merely because the current ref happens to match. A valid pending/unknown attempt can reconcile a lost response using an actual target reading, and repeated execution does not write again. Historical queries do not require current approval to remain valid, the current subject to remain unchanged, or execution budget to remain. They grant no new action and do not prove that the same state persisted afterward.

Local simulated delivery input remains `delivery-plan/v1`; stored plans without content proof use `delivery-proposal/v2`, and new plans with content proof use `delivery-proposal/v3`. `provider_snapshot` retains nonrecursive provider state and a digest of operations; `expected_provider` is the canonical digest of that snapshot. Action, parameters, source, target, and pre-state all contribute to the plan ID. New requests/receipts use `delivery-request/v2` and `delivery-receipt/v2`, respectively, binding the exact plan and resulting state; execution rechecks current capabilities and rollback data compatibility. A receipt confirms that particular local simulated action. A historical receipt cannot establish that the current artifact, target, or cohort has remained unchanged.

Older receipts, older delivery plans, and inconsistent records that lack these integrity bindings are explicitly rejected. Fields are not filled in automatically, IDs are not recomputed while reusing old approvals, and ledgers are not deleted. Retain the old records; after verifying the actual state, the host must explicitly authorize replanning/migration. Plans requiring a new action must obtain exact approval again; recovery queries and idempotency remain available for existing valid v2 attempts. Check applicability and budget reporting are described below. Optional [single-file content binding](../../docs/artifact-content.md) lets trusted policy require verification of actual SHA-256/length for new actions; source and build-configuration associations remain host declarations, not build authentication. Content plans use merge-proposal/v2 and delivery-proposal/v3; old labels/valid attempted operations remain queryable as stored, with no automatic upgrade or budget recount.

## Minimal Configuration and Records

### Budget Ledger and Invocation Observations

Successful CLI results and runtime-error results include `budget_report` (`lifecycle-budget-report/v1`), without changing the existing budget, statuses, or recommendations. Argument-parsing errors/help do not create a report; direct Python function calls do not automatically generate CLI reports. `budget_report` and top-level `authorizes_action` describe the response and are not part of the canonical plan; do not write the entire CLI response back as a ledger plan. The report has three distinct scopes:

- `ledger.scope=host_lifecycle_ledger` retains operations/rounds inherited across stages, without changing charging points or resetting them. The unit of `operation_attempts` is started_lifecycle_operation. begin-review counts both an operation and a round; ingest/import-security, adjudicate, advance, merge-prepare, the first merge-execute, delivery-plan, the first delivery-execute, and observe count an operation at their existing accounting points. Failures after accounting begins retain consumption; an earlier rejection may not have reached the accounting point. init only inherits usage; status/export/query, standalone preflight, and recovery of an existing valid operation do not add operations.
- `observed_work.scope=current_cli_invocation` observes this invocation's monotonic-clock wall seconds, Git subprocess attempts, repository scan attempts and entries actually traversed, and merge-tree write-tree attempts. Attempts are recorded before execution, retaining errors/timeouts and partial scans. Preflight embedded in execution shares the same observer without an additional charge. Preflight may write Git objects, so “no ledger increase” does not mean no work or a completely read-only filesystem. Zero means this invocation actually observed none of that item, not that historical or external work is zero.
- `external.cost` and `external.runtime_seconds` are both `{status: "unknown", value: null}`; model costs and total host-external runtime are not estimated. Observations are not written to the ledger, create no new hard limits, and do not claim to limit resource consumption for the entire filesystem scan.

Each ledger unit reports used/limit/remaining/exhausted. `capacity.next_operation` and `next_review_round` indicate only whether the existing counts can accommodate the next corresponding ledger increment; they do not replace a command's policy, evidence, approval, or state prerequisites. When the round count exactly reaches its limit, other already-permitted operations in that round can still be processed, but a new round cannot begin. Exceeding any applicable limit prohibits the corresponding new work. An all-green result in the last valid round may still be READY_FOR_NEXT; that does not bypass the budget for later execution. Every report has `authorizes_action=false`.

Counts are reported as known only when the policy pin, task, and loaded ledger bindings hold and the counts are valid. Missing/invalid historical counts are not filled with zero; they display unknown/null. Before every new charge, operations and rounds must both be exact nonnegative integers. Booleans, negative values, nonintegers, or missing fields cause rejection while preserving the original ledger; arithmetic must not convert bad data into normal counts. Valid integers above the limit retain the actual used value, with remaining clamped to zero. After a save failure, in-memory values are marked only as session_snapshot with durability=unknown, without claiming persistence; verify actual storage and receipts before retrying on the basis of capacity. Existing valid attempted operations remain queryable/recoverable idempotently even with exhausted budget or unknown counts; recovery grants no new action. There is no automatic ledger migration or backfill of historical observations.

The compatibility field `durability=persisted` means only that an ordinary save call succeeded or a locked reload observed the data; it does not independently prove durability through power loss. The added machine-readable scope descriptions do not change historical ledgers or cumulative counts. New real host-delivery actions additionally require a [durable capability checkpoint](../../docs/host-delivery.md#persistence-and-recovery); missing or uncertain checkpoints remain UNKNOWN/HOLD. Exact historical queries do not re-execute or incur duplicate charges when new capabilities are missing.


A complete runnable configuration is generated in a new directory by the project's own [fixture.py](../../validation/lifecycle/fixture.py). Its users, budgets, metrics, and times are **synthetic examples, not approved project defaults**. Real use requires the user/host to fill in the entire policy according to requirements; empty configuration never grants automatic clearance.

policy.json (`lifecycle-policy/v1`): task_id, risk, checks, budget, humans, reviewers, high_expert_count, low_auto, allowed_actions, merge, delivery. Each checks entry has id/stage(pr or merge)/gate(ci, semantic, security, integration)/scope/config/required/na_reason, with the optional versioned applicability record described below; the three PR gates and mandatory integration requirements must be explicit. budget is max_rounds/max_operations; handoff includes consumed values. Risk comes from user-confirmed impact and must not be downgraded by tools. Example numbers do not override established pilot limits or stricter host limits.

### Check Applicability and Optional Results

Ordinary applicable checks continue to use `na_reason: ""` without applicability. For a check to be inapplicable, the trusted host must provide the following record in the policy pinned by digest; the placeholder digest in this example cannot be used directly at runtime:

```json
{
  "na_reason": "",
  "applicability": {
    "schema": "check-applicability/v1",
    "reason": "Why this check does not apply",
    "basis": "Reference to host-verified rules or materials and the basis for applicability scope",
    "decider": "Decision maker verified and transcribed by the host",
    "source_subject_digest": "Digest computed by core.digest for the current source subject",
    "scope": ["Scope exactly matching this check.scope"]
  }
}
```

Reason, basis, and decider must not be empty or whitespace-only; scope must contain no duplicates and must match the check's scope. The check's ID, stage, config, task, and policy pin are bound by its containing policy. Output preserves the complete applicability record and policy association. The decider string does not authenticate a real person, and basis text does not automatically establish facts. The host must verify the actual basis first; tool logs cannot supply self-granted exemptions. A tool returning N_A cannot itself create an exemption or replace a high-risk expert's valid PASS, a required human decision, or disposition of a blocking finding.

Applicability is bound to the source subject; advance invalidates the old declaration. Merge preflight passes an explicit source identity only after verifying the candidate/source relationship. The declaration covers the combination derived from that source within the specified check scope; it does not claim to separately establish candidate-specific applicability, nor does it put a not-yet-generated candidate SHA into policy and create a circular binding.

Old nonempty `na_reason` values (including whitespace-only values) can still be loaded, but no longer grant exemptions: the corresponding check becomes UNKNOWN and requires explicit host revalidation. Missing fields, malformed records, scope/source mismatches, and conflicts between the old reason and new record also do not produce N_A. No basis is invented for old data, no pin is changed, no budget is reset, and no old approval is reused; read-only queries and idempotent recovery of valid historical receipts remain available. Policy changes after revalidation must preserve the old ledger and continuous usage, and handle migration explicitly under the existing pin/approval rules; this interface provides no automatic migrator. Explicit delivery-capability opt-outs still follow delivery policy.

PR/integration results display every configured check with required and blocking for each. Optional-check FAIL/UNKNOWN results remain visible but do not automatically block; required failures still block. Any unresolved formal blocking finding discovered by any check takes effect independently and cannot be closed by an optional label. Stage recommendations remain separate from execution authorization.

Initial `pre-pr-handoff/v1`: task_id, the five-field subject (base/head/worktree_digest/ci_config_digest/artifact_digest), budget(rounds/operations), requirements_ref, history_ref, findings. The host transcribes this after verifying original pre-PR evidence; importing a PASS alone is insufficient. Historical findings continue to be verified against the candidate and are not assumed resolved. State initialization is allowed only once; stage transitions do not reset the budget.

Optional `source_content` policy and handoff/advance sidecars bind the [source-directory/index/worktree manifest](../../docs/source-manifests.md) to the existing `worktree_digest`, without adding a sixth subject field. Old labels are not upgraded automatically; new actions recheck the source according to policy, while valid historical receipt recovery requires no new collection/charge. See that document for supported scope, configuration, and non-atomic snapshot limits.

`review-batch/v1` contains evidence and findings. See the [generator's evidence function](../../validation/lifecycle/fixture.py) for evidence fields: exact subject/config/scope/status/complete, observed_at/expires_at, provider/run/job/attempt/tool_version/context_id/reviewer, raw.path/sha256. Raw files have a 1 MiB/no-follow limit; their digests are verified and saved on import. This interface neither continuously monitors external raw files nor provides immutable storage; the host must archive the corresponding bytes for later audits. Partial, expired, wrong-object, or insufficient-coverage evidence does not become PASS. Evidence for the same check is grouped by provider/job/reviewer/context, with the latest observation selected by observed_at verified by the trusted host, not import order. run/attempt are opaque identifiers and are not used for sorting. Substantive conflicts between observations at the same time produce UNKNOWN until a later observation resolves them. A current failure/unknown for any required check still blocks and cannot be overridden by a PASS from another perspective; optional-check results remain visible. All old failures are retained, and high-risk reviewer counts are also checked against the latest valid attempts. Incremental work depends on actual identity and scope, not comment time. Reuse across identities requires the host to verify the relationship and import a new proof record retaining the original source, rather than directly changing an old PASS's subject.

Candidate fields: id/subject/location/trigger/impact/severity/confidence_basis/attribution/attribution_basis/source/evidence_refs. If no location is available, explicitly state “unable to locate” and explain the source; do not silently discard off-diff findings. Candidates block by default until host verification. A trusted reviewer supplies `finding-decision/v1` in host-root with actor/subject/finding/fact/disposition/blocking/reason/evidence_refs/duplicate_of. Closure requires current, complete verification evidence; merely saying deferred/intentional/risk accepted cannot close a finding, and this reference implementation does not yet provide exemption controls. Deduplication retains both observations/decisions and their relationship, without voting. New observations can reopen findings; absence does not automatically resolve them. The program checks verification-record associations, not the truth of their semantics.

`subject-change/v1`: subject, impact, reused_evidence (the current list for direct relabeling must be empty). After checking impact, proof can be reimported instead of automatically rerunning every check. Old evidence is retained but does not directly apply to the new identity. Without reliable impact evidence, both resolved and refuted nonblocking dispositions return to pending verification. Every version-bound approval is rechecked. High risk requires valid reports from multiple policy-specified reviewers and different contexts, plus a human decision; strings alone cannot guarantee context independence.

authority.json (`host-authority/v1`) contains decisions, each with id/actor/kind/action/binding/policy_sha/decision/expires_at. PR/merge approval binding is the SHA-256 of the corresponding subject's canonical JSON; merge-prepare binding is the digest of the repository/base/head/policy_sha object; merge-execute binding is the stored plan.id; delivery-action binding is the delivery plan.id. Canonical digests are generated by core.digest. The example grant function **simulates human records for tests only and must not be used to forge real approvals**. See the fixture policy for allowed actions; a command is not authorization.

Original security B integration: `security-import/v1` contains check and record (an existing security-evidence/v1 JSON under the input root). import-security parses and hashes bytes from the same read, binding request_binding/subject/config/scope/raw without treating authorizes_progress as approval. Candidates continue through verification; missing bindings are rejected. There is no native SARIF/CI parser.

### Attempt Details and Save Failures

The ledger remains `lifecycle-state/v1`. New charges add `attempt-started` to the existing `events`, with detail using `lifecycle-attempt/v1`: unique `attempt_id`, the post-charge operations ordinal `sequence`, a fixed `operation` label, and `round_delta`; the event's `at` records the time. This record and the operations/rounds increment are saved in the same atomic file replacement, adding no charging point. Fixed labels contain no raw command arguments, paths, or evidence bodies. Later business events link to the same `attempt_id`; saving pending also records `merge-requested` / `delivery-requested` events bound to the exact plan ID, without changing existing receipt/request schemas or approval bindings. started proves only that accounting began, not that processing completed or an external action succeeded.

`budget_report.current_attempt` describes only this invocation's new attempt and its durability. It is null for read-only queries, old ledgers, or when no new charge has begun; this must not be interpreted as zero historical consumption. Old cumulative counts remain unchanged; old details are not fabricated, and counts are neither inferred nor reset from the new details. The direct API `Session.charge(rounds)` accepts only the exact integers 0 or 1. Negative values, bool, float, other increments, and uncontrolled labels are rejected before changing memory/disk. The CLI already used fixed increments; this is a defensive measure in the underlying API, not a demonstrated remote budget bypass.

Any Session ledger-save exception retains unknown durability and locks the session against subsequent saves, charges, merge/delivery execution, and result queries. After catching the exception, in-memory pending must not be treated as a persisted intent. Nor may memory be blindly rolled back on the assumption that disk is unchanged: the file replacement may have completed before the error was reported. Exit the current lock scope, then successfully enter `locked()` to verify policy and reload disk. Budget exhaustion in a normal session does not affect the existing safe query paths; the save-failure lockout is a separate condition from budget limits.

Recovery follows the actual persistence boundary: started without pending means execution intent was not yet accepted, and restarting the operation creates another attempt at the original charging point. An existing valid pending/receipt permits only query reconciliation, without re-execution or another charge. When an action completes but its response/final ledger save is lost, recovery still uses the existing actual ref/provider state and strict bindings; the new details do not grant authorization. If a known action outcome itself could not be saved, its lost fact cannot be reconstructed from details after restart; matching state does not prove who wrote it. Existing persisted failure receipts continue to reject confirmation under the original policy, and old receipts lacking bindings are not automatically upgraded. The 1 MiB limit remains in force; growth to the limit causes an explicit stop for host handling that preserves history, without deleting events to make room. External costs/tokens/total runtime remain outside these details and unknown.

## Executable Entry Points

From the project root:

```sh
python3 -B interfaces/lifecycle/cli.py --help
python3 -B validation/lifecycle/fixture.py /tmp/my-new-lifecycle-fixture --trusted-fixture
```

The second command accepts only a nonexistent directory and creates project-owned files, bare Git without a remote, and local test commits. It outputs host/inputs/policy_sha; use the actual output values rather than guessing paths:

```text
python3 -B interfaces/lifecycle/cli.py --host-root HOST --policy-sha SHA --input-root INPUTS --record handoff.json init
```

HOST/SHA/INPUTS above are explanatory parameters that must be replaced. Select later commands in order; the entire sequence need not be rerun each time:

1. begin-review records usage before a new round; ingest imports tool/Agent evidence; adjudicate reads host verification decisions; pr-status determines the recommendation for entering integration; export produces a handoff with history (publication is always NOT_RUN).
2. merge-prepare reads `merge-plan/v1` (base/head/integration_artifact), requires prepare authorization, and produces candidate/combination subject. Import integration evidence for that combination and obtain exact human approval and execution authorization before merge-preflight/merge-execute; use merge-query first for uncertain or repeated requests. CAS failure requires preparing/verifying again, without automatic retry or switching tools. A change to the complete source_subject (not just base/head) invalidates the plan. commondir, alternates, symbolic paths, and symbolic targets are rejected; updates use --no-deref. Tool errors are distinguished from real conflicts; Git operations have a 10-second timeout, and unconfirmed results must be queried first.
3. delivery-plan reads `delivery-plan/v1` (action/parameters) and only generates a plan. After exact authorization is recorded in trusted authority, use delivery-execute --operation ID and delivery-query for the same ID. deploy requires a confirmed merge receipt and the same verified artifact. Both promote and enabling a flag require the current artifact to be associated with this task's verified merge combination and a deployment receipt for the same target; promote also requires a valid observation. Source contributes to the plan ID and is reverified during planning and execution; an unrelated initial artifact cannot borrow the current PR's passing conclusion. Old plans/deployment records lacking source fields cannot inherit them automatically; they require replanning and deployment, while completed actions remain queryable. Planning and execution of advancing actions both recheck current blocking/PR conditions; existing action authorization does not exempt new findings. The initial flag-set cohort is policy-defined; expansion requires observation. pause only pauses automation and does not reduce exposure; rollback requires a confirmed compatibility mapping for the current data_version; forward-fix only creates a repair-handoff receipt, without claiming that code has been fixed/deployed.

Delivery parameters: deploy/rollback={artifact}; promote={artifact,channel}; flag-set={enabled,cohort}; pause={}; forward-fix={finding_ids,handoff_ref}. The simulated provider reads/writes only host-root/sim-provider.json and does not connect to production. Delivery as a whole and its individual capabilities are separately opt-in; required capabilities cannot be disabled. A disabled module returns NOT_RUN/HOLD, not production acceptance.

observe reads `observation/v1` from input-root: artifact/target/cohort/config/window_start/window_end/source/query/samples/value/complete/observed_at. Policy observation explicitly specifies duration_seconds/min_samples/max_value/max_age_seconds/source/query, with the window anchored from the current provider effective_at to that time plus duration_seconds; a window earlier than configuration activation cannot be used. Source, samples, and finite thresholds must match; insufficient data, wrong targets, expiration, and NaN do not pass. There is no indefinite wait; insufficient data at window end is handed to the owner/replanned. Default delivery-status interprets simulated results; when a host provider is selected, it interprets only receipt/current-state consistency for its supported operations, leaving other required capabilities UNKNOWN. Neither provides a production-health guarantee.

## Temporary Files After Forced Termination

`temp-report` provides a locked, bounded, metadata-only check for residual files, without relying on a parseable ledger. It does not delete, restore, or replay any record, nor determine budget or approval validity. Ownership of all historical residual files is UNKNOWN and remains for host handling. See [temporary-state inspection](../../docs/temporary-state.md) for commands, limits, and prerequisites for later cleanup.

## Optional Build-Provenance Verification

The [build-provenance contract](../../docs/build-provenance.md) adds a policy-selected verifier interface injected by a trusted Python host, beyond content digests and host declarations. The default CLI loads no verifier; missing required capabilities return UNKNOWN/HOLD. Plans with verification results use merge-proposal/v4 and delivery-proposal/v4, binding the exact source, combination tree, configuration, artifact, run, and action intent. New execution rechecks them; existing valid attempts query history only, without another charge or re-execution. Real signature/CI identity authentication is not built in, and the synthetic delivery provider remains simulated.

## Optional Trusted Host Delivery Interface

The [host-delivery contract](../../docs/host-delivery.md) accepts trusted application objects through `Session(..., delivery_providers={id: provider})`, with fixed policy selecting the version and target. The first version supports only deploy/rollback. New actions require actual content proof, exact approval, and provider conditional-update/durable-idempotency capabilities; the default CLI injects no objects. Separate host-delivery plan/request/result versions are used; old simulation records are not upgraded to real delivery. Existing attempts query results only, without resending or charging again; unknown results block new intent for the same target. Interface tests use synthetic providers and do not mean production services are integrated.

Optional `Session(..., temporary_namespace=...)` accepts only a controlled temporary namespace created by the trusted host and matching the root/policy. It registers new staging resources; recovery requires separate exact record authorization and is neither business recovery nor whole-directory cleanup. It currently supports only POSIX and depends on an exclusive cooperative namespace; Windows is conservatively rejected. Default behavior is unchanged. See the [temporary-state documentation](../../docs/temporary-state.md) for use and trust boundaries.
